# Worked solutions and independent checks

Attempt [the exercises](../EXERCISES.md) first. These are original analyses of the teaching format, not source quotations.

1. The Python string is encoded into frame bytes in process memory. An unbuffered file write requests OS output; bytes may remain in the kernel/device caches. `fsync` requests persistence through the OS interface. A later `recover()` reads the filesystem's current view, which may still come from cache. No physical power interruption is performed, so recovery alone cannot validate media durability.
2. `300 = 1×256 + 44`, so four bytes are `00 00 01 2c`. UTF-8 encodes some characters in multiple bytes. A length of one for `雪` would make the next two bytes look like part of a following field. Always encode first and count the resulting bytes.
3. Compact payload `[["put","a","1"]]` has 17 ASCII/UTF-8 bytes. `16+17+4=37` frame bytes; starting at byte 7, the next offset is `7+37=44`. This can be checked by calling `encode_transaction(1, [("put","a","1")])` and taking its length.
4. The final mapping has `x="2"`; deleting an absent `y` does nothing. Ordered updates within a valid transaction are permitted. The format stores strings, so treating `"2"` as a number is an application decision.
5. The frame boundary concerns recoverable bytes; acknowledgement concerns knowledge conveyed to the caller. A complete frame can exist after the process loses the response, or after sync fails with an uncertain outcome. Neither means the caller observed success.
6. Transaction 1 ends at byte 62. Cuts 0,15,16,30,53 of transaction 2 all return `a="10",b="20"`, valid boundary 62. Cut 0 has no trailing bytes; cuts 1–15 report incomplete header; cuts 16–53 report incomplete body/checksum. Cut 54 returns `a="9",b="21"`, valid boundary 116 and no trailing bytes. A reader does not mutate the file; opening for append refuses incomplete trailing bytes unless repair is explicitly chosen.
7. Use `[["put","a","9"],["put","b"]]` with a correctly computed CRC. Immediate application sets `a` before discovering the second operation's missing value. Correct code validates the complete operation list into a temporary representation first, then applies it. A checksum checks encoded bytes, not operation semantics or conservation rules.
8. In one history the partial frame is discarded; retry applies the operation once. In another, the first frame is complete and replayed even though its acknowledgement was lost; a second representation of the same transfer could apply it twice. A persisted unique request ID with its result, checked and stored atomically with the business update, lets the server return the previous result. That requires defining request-ID scope, reuse, retention and mismatch behavior. This project does not implement it.
9. A `TXN1` byte pattern may occur within payload text. Even a genuinely valid later transaction cannot justify a missing/corrupt predecessor. Sequence and application invariants would be uncertain. `repair_tail=True` addresses only an explicitly incomplete final frame; it is not a policy for deleting evidence of corruption.
10. All remaining frames still form a valid prefix. The file has no independent statement of how long it should be. An independently durable expected commit ID or external signed receipt could detect loss of an acknowledged suffix, with its own trust and persistence assumptions. A checksum stored inside the deleted suffix disappears with it; that does not help.
11. One candidate protocol: freeze or serialize writers; replay a valid map; write a complete versioned snapshot to a distinct temporary file; request file sync; install it with an appropriate same-filesystem atomic replacement; request parent-directory synchronization where supported; only then retire the old recoverable representation. Each crash point must leave either the old history or a valid new snapshot and an unambiguous generation policy. A rename alone does not establish durable namespace installation, and reopening snapshot state must be designed with subsequent transaction IDs. Truncating the only old log before the new file is durable can lose both. This is a design answer, not an implemented, portable compaction proof.
12. The executed fixture has a 54-byte second frame: cuts 0–53 all preserve the old mapping; cut 54 exposes the entire new mapping. Retaining a fixed key count isolates accumulated history cost from live-map growth. Expected growth is broadly linear in encoded history for this parser, but small runs have fixed overhead, caches and scheduling can distort ratios, and CPU frequency/allocation can vary. The dated evidence stores five samples per size; your values should differ. Warm replay samples do not estimate storage write bandwidth.
13. Both writers may encode ID 9 and append two complete frames. Replay rejects the second ID 9. Without interprocess serialization their partial writes may instead interleave inside a frame, producing corruption; one writer's repair could also truncate another's valid append. A local exclusive lock, acquired before recovery and retained through close, can serialize cooperative writers if its OS semantics and failure release are verified. An in-process mutex alone does not coordinate separate processes, and an advisory lock does not stop uncooperative modification. The baseline instead requires exclusive caller ownership and does not enforce it.

## Reconstruction check

A reader rebuilt from memory should agree with the reference on empty history, Unicode values, ordered replacements, every proper byte prefix of a batch, corrupt complete frames, malformed operations, and missing IDs. Agreement on happy paths alone is insufficient. A disagreement is a debugging result: preserve the input and explain which invariant chooses the expected behavior.
